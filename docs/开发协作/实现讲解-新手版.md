## 0. 先记住一句话

> **数据是核心,界面只是把数据"画"出来。**

这句话贯穿整个项目。下面是我们的"数据":

```cpp
struct Component {      // 一个元件
    GateType type;      //   什么门(与/或/非/异或/与非/或非/开关/灯/自定义)
    int x, y;           //   画在哪儿
    int id;             //   编号(显示成 U1、U2...)
    bool state;         //   开关的开/关
    wxString customName;//   自定义元件的名字
    int truth;          //   自定义元件的真值表
};

struct Wire {           // 一根连线
    int comp1, pin1;    //   起点:哪个元件、哪个引脚
    int comp2, pin2;    //   终点
};
```

画布上所有东西,就是"一个元件列表 + 一个连线列表"。
保存文件、导出网表、仿真,全都是在读写这两个列表 —— 和界面无关。

## 3. 本轮补齐的三个功能(重点)

这三件事之前"有壳无实":控件都在、菜单项都在,但点下去没真功能。

### 3.1 属性表:回调函数让画布"打电话"

**问题**:属性表在主窗口(`MyFrame`)里,但"选中了哪个元件"这个信息在画布(`DrawingCanvas`)里。主窗口怎么知道该刷新了?

**笨办法**:主窗口定时轮询("你选了吗?你选了吗?...") —— 浪费、别扭。

**我们的办法**:**回调**。画布留一个"电话号码",任何变化时拨一下:

```cpp
// DrawingCanvas.h —— 画布说:"谁想被通知,就把函数给我"
std::function<void()> onSelection;
void SetSelectionCallback(std::function<void()> cb) { onSelection = cb; }

// DrawingCanvas.cpp —— 内容一变就拨号
void DrawingCanvas::NotifyChanged()
{
    InvalidateScene();               // 标记静态图需要重建，再请求重画
    if (onSelection) onSelection();  // 打电话给主窗口
}
```

```cpp
// MyFrame.cpp —— 主窗口登记自己的号码
canvas->SetSelectionCallback([this]() { RefreshPropertyTable(); });
```

`[this]() { ... }` 是 **lambda 表达式**(匿名函数),`[this]` 表示"我要用当前对象的成员"。

**关键设计**:画布只知道"有人要通知我",**不知道**是谁 —— 所以画布不依赖主窗口。这个方向叫"依赖倒置",是解耦的常用手法。

**效果**:选中/拖动/仿真/撤销/粘贴……任何变化,属性表都自动刷新。属性表显示:
名称、类型(自定义元件显示"自定义(名字)")、位置、状态/输出,自定义元件还多 4 行真值表。

### 3.2 撤销/重做:存快照,别写"反操作"

**问题**:怎么实现撤销?

**笨办法**:为每个操作写一个"反操作" —— 放置的反操作是删除、删除的反操作是"记住删了什么再放回去"、拖动的反操作是"记住原来在哪再拖回去"、连线的反操作是删线……
每种操作都要写两遍代码,又多又容易错。

**我们的办法**:**快照式**。因为我们已经验证"电路 → JSON 文本 → 电路"是无损的,所以:

> 每步改动之前,先把当前电路存成一段 JSON 文本压进栈;
> 撤销 = 把栈顶那段旧文本读回来。

```cpp
void DrawingCanvas::PushUndo()                 // 改动前调用
{
    undoStack.push_back(CircuitToJson(components, wires));
    if (undoStack.size() > 100) undoStack.erase(undoStack.begin()); // 只留最近100步
    redoStack.clear();                          // 有了新动作,重做链失效
}

bool DrawingCanvas::Undo()
{
    if (undoStack.empty()) return false;
    redoStack.push_back(CircuitToJson(components, wires)); // 当前状态留给"重做"
    wxString snap = undoStack.back(); undoStack.pop_back();
    RestoreSnapshot(snap);
    return true;
}
```

**两个细节**:
- **拖动**:只在按下时存快照,松手时比较"内容变了没",没变就不入栈 —— 否则"点一下选中"这种没有改动的动作也会污染撤销链。
- **栈深 100**:上限,防止长时间使用内存无限增长。

**这个思路的价值**:一份代码覆盖所有操作(放置/删除/拖动/连线/粘贴),以后加新操作也不用改撤销逻辑。

### 3.3 用户自定义元件:4 个复选框 = 一张真值表

**任务要求**:"支持用户自定义元件"。之前只有写死在代码里的与/或/非门,用户没法自己造。

**核心洞察**:**2 输入 1 输出的逻辑电路,行为完全可以由真值表描述**。
一共只有 4 种输入组合(A=0B=0 / A=0B=1 / A=1B=0 / A=1B=1),
每种组合的输出是 0 还是 1,4 个勾选框就能定完 —— **这样就能定义任意 2 输入逻辑!**

我们把这张表打包成一个整数存起来(位运算):

```
truth 的二进制位    bit3 bit2 bit1 bit0
对应的输入组合      (1,1)(1,0)(0,1)(0,0)      ← 组合编号 i = A*2 + B
例:与门             1    0    0    0     = 8
例:与非门           0    1    1    1     = 7
```

```cpp
// 仿真时:算出输入组合编号 i,取 truth 的第 i 位
else if (c.type == GATE_CUSTOM) {
    int idx = v0 * 2 + in(c, 1);   // v0=输入引脚0的值,in(c,1)=引脚1的值
    res = (c.truth >> idx) & 1;    // 取第 idx 位
}
```

**数据怎么流动**(整个功能的链路):

```
用户勾真值表        → 自定义元件对话框(CustomDialog.h)
  → 存进 customDefs 列表,并在元件库树上挂一个节点
  → 点击该节点 → 画布进入"放置模式",记住名字和真值表
  → 点击画布 → 生成一个 type=CUSTOM 的 Component(带 name+truth)
  → 存盘时 name/truth 一起写进 JSON
  → 读盘时一起读回来(老文件没有这两个字段也能读,见 3.4)
```

**顺带一提**:网表里自定义元件只写它的**名字**(不写真值表)。
这跟真实 EDA 软件一致 —— 网表只说"这里用了某某型号的元件",具体行为由元件库提供。

### 3.4 写严格、读宽容

给存档新增 `name`/`truth` 字段后,老存档(没有这两个字段)就解析失败了。
**这是绝对不能接受的**:用户之前存的文件必须还能打开。

解决:正则里把新字段写成**可选组**,读的时候判断"匹配到了没":

```cpp
// (,"name":"...","truth":N)?  ← 问号表示"可有可无"
std::regex compRe("...\"state\":(\\d)(,\"name\":\"([^\"]*)\",\"truth\":(\\d+))?...");
// 读的时候:
c.customName = (*it)[7].matched ? ... : wxString();   // 没匹配到就用默认值
c.truth      = (*it)[8].matched ? std::stoi((*it)[8]) : 0;
```

工程界把这叫 **Postel 定律**:"发送时要保守,接收时要宽容"。
越界的输入、旧版本的文件,都尽量兼容 —— 否则你的软件会三天两头"打不开文件"。

## 3.4 网表:一根线 ≠ 一个网络(一个重要修正)

**先讲背景**:一开始我们把"每根连线 = 一个网络"直接写进了网表。

**问题出在"扇出"**:一个输出接多个输入是电路里的常态。半加器里开关 `SW_A`
同时接到 XOR 和 AND,我们画了 **2 根线**,但电气上它们是**同一个网络**。
按老写法,`U1` 的引脚 1 会出现在**两个网络**里 —— PCB 软件看到"同一个焊盘属于两个网络",
会当成短路/冲突报错。**网表是给机器读的,语义错了它不会给你面子。**

**正确做法**:把"连线"归并成"电气网络"。用**并查集**(union-find):

> 每根连线把两端"合并到同一组";最后同一组的引脚就是一个网络。

```
画布上的连线                     并查集归并后的网络
U1[0] -- U3[0]                  net1: U1[0] + U3[0] + U4[0]   ← 3 个节点
U1[0] -- U4[0]        ==>       net2: U2[0] + U3[1] + U4[1]   ← 3 个节点
U2[0] -- U3[1]                  net3: U3[2] + U5[0]
U2[0] -- U4[1]                  net4: U4[2] + U6[0]
...
```

导入时反过来做:一个网络有 N 个节点 → 重连成 N-1 根线(链式),电气上等价。
**必须"块内配对"**:把所有节点拉平再两两配对,会把上一个网络的节点和下一个网络的
节点连到一起 —— 这是我们真实踩过的 bug,现在单元测试里专门盯着它。

## 3.5 让网表真的"能被 KiCad 加载"(对齐真实格式)

任务要求"导出标准网表文件,该文件能够被 PCB 软件加载"。光靠自己"觉得对"不算数,
我们做了三件事:

**第一件:让 KiCad 自己导出一份参考网表,逐字段对比。**
用 KiCad 的命令行工具,从一张最小原理图导出网表:

```bash
kicad-cli sch export netlist --format kicadsexpr -o ref.net ref.kicad_sch
```

对比后发现我们少了 4 样东西,全部补齐:

| 项目 | KiCad 的写法 | 为什么要紧 |
|---|---|---|
| 网络分组 | `(net ... (class "Default"))` | PCB 软件靠 class 套用线宽/间距规则 |
| 节点电气类型 | `(node ... (pintype "input"))` | 告诉 PCB 软件这个脚是输入还是输出 |
| 引脚编号 | 从 **1** 开始 | 必须和 PCB 焊盘的编号(Pad 1、2、3)对得上,否则连不上 |
| 元件库段 | `(libparts (libpart ...))` | PCB 软件从库里取引用号前缀和引脚类型 |

**第二件:兼容真实网表的写法(读宽容)。**
我们的导入器原来只认自己导出的格式,读 KiCad 的网表会失败,原因有两个:
- 正则里写死了**单个空格**:`(comp (ref "U1")`,而 KiCad 是**每个字段单独一行** → 改成 `\s+`
- 写死了 **U 前缀**:真实网表里是 `R1`、`C3` 混排 → 改成通用前缀,并按"前缀+编号"建映射;
  同号不同前缀(比如 R1 和 C1)会自动分配不冲突的编号

**第三件:用 KiCad 的真实网表做互操作测试。**
单元测试里内嵌了 KiCad 真实输出的缩略版(保留换行缩进、R 前缀、1 起引脚号这三处"坑"),
断言我们能把元件、网络、引脚映射全部读对。

> **老实说**:最后一公里的"在 KiCad 图形界面里点导入、看到元件和网络出现在 PCB 上"
> 只能人工做一次 —— KiCad 没有提供命令行/脚本的网表导入接口。
> 但格式已按 KiCad 自己的输出对齐、并用真实网表验证了双向解析,导入失败的概率很低。

## 3.7 导出 KiCad 原理图(.kicad_sch)——让"能被 PCB 软件加载"看得见

**为什么还要加这个**:KiCad 6 以后的"正统"流程是

```
原理图 --(工具 → 从原理图更新 PCB / 快捷键 F8)--> PCB
```

从文件导入网表虽然还在(PCB 编辑器 → 文件 → 导入 → 网表),
但原理图这条路更直观:打开就能看见元件符号和连线,演示/答辩时一目了然。

**实现要点(两个坑)**:

1. **坐标精度**:导出的"引脚位置"和"导线端点"必须在 KiCad 里是**同一个点**,
   差一点点就连不上。做法是全程用**纳米整数**计算,打印时按 6 位小数输出
   (1px = 0.127mm = 127000nm,所有偏移都是整数,打印无损)。
   引脚和导线端点都由同一组整数算出,天然严丝合缝。

2. **符号库的命名规则**:`lib_symbols` 里每个符号内部的"单元"名要用**短名**
   (`SW_0_1`),不能带库前缀(`MyEDA:SW_0_1`)—— 写错 KiCad 直接报"加载原理图失败"。
   这个错误没有任何提示信息,只能靠和 KiCad 自己导出的文件对比才能发现。

**怎么验证它真的能被 KiCad 用?** 用 KiCad 自己的命令行工具回读:

```bash
# 1) 我们把电路导出成 KiCad 原理图
test_sim.exe --export-kicad-sch 样例/半加器.eda 样例/半加器.kicad_sch
# 2) 让 KiCad 加载这份原理图,并导出它自己算出来的网表
kicad-cli sch export netlist --format kicadsexpr -o out.net 样例/半加器.kicad_sch
# 3) 对比两个网表的"网络集合"
```

实测结果(半加器):

```
我们导出的网络数: 4
    [(U1,1), (U3,1), (U4,1)]     ← 开关A → 异或门输入1 + 与门输入1(扇出)
    [(U2,1), (U3,2), (U4,2)]     ← 开关B → 异或门输入2 + 与门输入2
    [(U3,3), (U5,1)]             ← 异或门输出 → 灯(和)
    [(U4,3), (U6,1)]             ← 与门输出   → 灯(进位)
KiCad 提取的网络数: 4
    [(U1,1), (U3,1), (U4,1)]
    [(U2,1), (U3,2), (U4,2)]
    [(U3,3), (U5,1)]
    [(U4,3), (U6,1)]
两边完全一致
```

**这就是"能被 PCB 软件加载"的硬证据**:不是"我们觉得格式对",
而是 KiCad 自己把我们的原理图读进去、算出连通关系,结论和我们一模一样。

界面里也有入口:**文件 → 导出 KiCad 原理图(.kicad_sch)**。

## 3.8 从网表到 PCB:把最后一步走通(封装这个大坑)

前面 3.5 节证明了"网表能被 KiCad 读"。但真去 KiCad 里导入时,会撞上这个:

```
错误: 无法添加 U6 (没有分配封装)。
总计告警: 0   错误: 6
```

**"封装"(footprint)是什么**:网表只描述"谁和谁相连",但元件在电路板上是什么形状、
有几个焊盘、每个焊盘在哪 —— 这些由"封装"描述。没有封装,PCB 软件不知道把元件
摆在板子上的什么位置、更没法布线。

**坑在哪里**:我们以为把封装写进 `(fields (field (name "Footprint") "..."))` 就够了,
其实 KiCad 的导入程序读的是**紧跟 `(value ...)` 的那个独立的 `(footprint "...")`**:

```
(comp (ref "U1")
  (value "SW")
  (footprint "Button_Switch_THT:SW_PUSH_6mm")   ← 这个才是导入时读的
  (fields
    (field (name "Footprint") "Button_Switch_THT:SW_PUSH_6mm")  ← 这份是给人看的
    ...
```

这个结论不是猜的:让 KiCad 自己导出一份"指定了封装"的原理图网表,逐字段对比就能看出来。

**我们的做法**:给元件加默认封装(都是 KiCad 自带标准库里的真实封装):

| 元件 | 默认封装 | 为什么 |
|---|---|---|
| 与/或/非/异或门 | `Package_DIP:DIP-14_W7.62mm` | 逻辑门当成 14 脚 DIP(类似 74 系列芯片) |
| 开关 | `Button_Switch_THT:SW_PUSH_6mm` | 轻触按键,2 个焊盘 |
| 指示灯 | `LED_THT:LED_D5.0mm` | 5mm 直插 LED |

## 4. 调试故事(比代码更值钱的方法论)

### 4.1 单元测试抓到了真 bug

写自定义元件时,单元测试报告:

```
[FAIL] ROUNDTRIP type  got=0 want=1
```

意思是"自定义元件存盘再读回来,类型变了"。查代码发现 `GateTypeName()` 里漏了 `GATE_CUSTOM` 分支:

```cpp
inline wxString GateTypeName(GateType t) {
    if (t == GATE_AND) return "AND";
    ...
    if (t == SW_INPUT) return "SW";
    return "LED";        // ← 自定义元件掉进这里了!存盘变成了 "LED"
}
```

**手点界面很难发现这个 bug**(要"存一个自定义元件 → 重开 → 仔细观察类型"),但单元测试 1 秒就抓到了。这就是"把逻辑做成纯函数 + 写测试"的回报。

### 4.2 二分注释法

界面出问题时(比如弹了个莫名其妙的断言框),**不要盯着代码干看**:
把可疑代码**注释掉一半**,重新编译运行,看问题还在不在 —— 在,说明问题在另一半;不在,说明就在这一半。
再对那一半重复,两三轮就能锁定到具体几行。

### 4.3 两个坑(踩了很久才想明白)

**坑一:模态对话框会"禁用"主窗口。**
我们测试时不小心让一个"另存为"对话框一直开着,之后所有的模拟点击都**静默失效** ——
因为 Windows 的模态对话框会把主窗口禁用,点击根本送不进去。
排查了很久才发现。**教训**:看到"点击没反应"先想想"是不是有对话框开着"。

**坑二:DPI 缩放的坐标换算。**
这台电脑桌面缩放是 **150%**。而我们的程序是"DPI 不感知"的老式应用,于是:
- 自动化脚本里取的窗口矩形是**物理像素**;
- 程序内部使用的坐标是**逻辑坐标 = 物理像素 ÷ 1.5**;
- 鼠标点击用物理坐标,程序收到的客户区坐标 = (物理 − 窗口原点) ÷ 1.5。

不换算,点击就"偏"了,还会出现"元件明明在文件里却看不到"——
因为窗口设成 1800×1150 物理时,程序内部只有 1200×767 逻辑,画布只有 754 宽,
坐标 480 的元件刚好在可见区,坐标 700 的就被裁到窗口外了。

**普通人用不到这个知识,但你要做 GUI 自动化测试/被老师问"为什么点击不准"时,这就是答案。**

## 6. 数据文件长什么样

```json
{
  "components": [
    {"id":1,"type":"SW","x":200,"y":250,"state":1,"name":"","truth":0},
    {"id":3,"type":"CUSTOM","x":480,"y":340,"state":0,"name":"MYAND","truth":8},
    {"id":5,"type":"LED","x":700,"y":340,"state":0,"name":"","truth":0}
  ],
  "wires": [
    [1,0,3,0],
    [3,2,5,0]
  ]
}
```

- `components`:每个元件一行,id 是编号,type 是类型,xy 是坐标。
- `wires`:每根连线四个数 `[起点元件, 起点引脚, 终点元件, 终点引脚]`。
- 引脚编号约定:与/或/非/异或/与非/或非门 `0=上输入 1=下输入 2=输出`;非门 `0=输入 1=输出`;开关/灯只有一个引脚(编号 0)。

## 连线预览的绘制优化

`DrawingCanvas::OnPaint()` 使用双缓冲，并把背景擦除交给绘制过程，避免先清空屏幕再逐个绘制造成闪烁。网格、已完成的连线和元件缓存在位图中；只有电路内容、选择、仿真状态或窗口尺寸发生变化才重建。

鼠标移动仅更新预览终点，刷新旧线和新线的覆盖区域；刷新请求异步处理，可以合并密集的鼠标事件。第一下点中引脚时将终点初始化到起点，Esc 和切换工具会清除预览，避免跳线和残影。

交互回归测试 `MyEDA/test/test_canvas.cpp` 在真实画布上比较像素，覆盖起点初始化、取消、切换工具、四向移动、完成连线、撤销重做和窗口缩放。它需要已解锁且无遮挡的 Windows 桌面，会短暂显示测试窗口，运行时不要移动鼠标或切换窗口。先完成正常构建，然后在能找到 CMake 的终端中执行：

```powershell
cmake --build MyEDA/build --config Debug --target test_canvas
.\MyEDA\build\Debug\test_canvas.exe
```

测试未纳入日常无窗口的 `build.bat`；64 项逻辑与文件测试仍由原入口运行。像素回归通过不代表测量了所有机器上的帧率，流畅度仍需在实际电路规模下体验。
